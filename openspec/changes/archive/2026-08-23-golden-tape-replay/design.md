# Design — golden tape record and replay

## Context

Aeron Cluster already journals every ingress message (the Archive writes segment files;
the RecordingLog maps log positions to recordings), and already replays the whole log
through `OmsClusteredService` on any restart without the clean flag. Replay is
deterministic because timestamps come from the log, and the echo service's output *is*
the sequenced timestamp — so expected outputs are derivable at record time. What is
missing is a preserved tape, captured expected outputs, and assertions.

Two facts constrain the design, both verified on this machine:

1. A tape can never be regenerated byte-identically — record-time timestamps are wall
   clock. The tape is a preserved artifact, not a build product.
2. A 3,000-heartbeat recording is one 128 MiB segment file that is sparse: ~376 KiB of
   real blocks. Git does not preserve sparseness, so the raw file cannot be committed.

## Goals / Non-Goals

**Goals:**
- Freeze one known-good heartbeat journal under `journal/`, small and immutable.
- Replay it against the bare state machine and against the real cluster recovery path,
  asserting count and outputs both ways.
- Benchmark replay throughput of both modes with recorded machine metadata.

**Non-Goals:**
- Snapshots (`onTakeSnapshot` is still empty; replay is always from position 0).
- Pipelined load generation, multi-node clusters, or general log-tailing tooling
  (`ideas/sbe-log-tool.md` stays parked; this reader may seed it later).
- A stored history of benchmark results (open question in
  `ideas/perf-regression-harness.md`).

## Decisions

### D1 — Tape format: sparse tarball, not raw files, not smaller segments

`journal/<name>.tar.gz` made with GNU `tar --sparse`, holding `archive/` and
`consensus/` (excluding `*-mark.dat`, which is runtime liveness state), plus
`manifest.txt` and `golden-outputs.txt` beside it, uncompressed and reviewable.

- Raw committed files: rejected — git materializes 128 MiB of zeros on checkout.
- Recording with a small `segmentFileLength`: rejected for now — it needs a config
  code change and interacts with term-length multiples; the tarball needs neither.
- Sparse tar: a few hundred KiB in the repo, restores sparse, zero code change.

### D2 — App-mode replay reads the segment file directly

The replayer walks the recording's data frames (32-byte `DataHeaderFlyweight` headers,
padding frames skipped), unwraps the cluster's `SessionMessageHeader` framing
(schema 111) to reach the app payload (schema 1), and calls `onSessionMessage` on a
bare `OmsClusteredService` with a capturing session.

- Alternative — standalone Archive + `AeronArchive.replay()`: uses only public client
  APIs, but drags a media driver and archive into the "bare app" benchmark, making it
  a near-duplicate of cluster mode. Rejected for this purpose; it remains the right
  tool if direct reading ever breaks.
- Cost accepted: ~150 lines coupled to Aeron's frame format, which is
  protocol-versioned and stable. The golden tape itself is the regression test for
  this coupling.
- The binary lives in `//cluster-node` as a second `java_binary`, because that is the
  one package allowed to depend on `//cluster-service` — visibility stays untouched.

### D3 — Cluster-mode measurement: opt-in counting wrapper

A delegating `ClusteredService` wrapper (same pattern as `FailFastClusteredService`)
counts applies and records first/last apply `System.nanoTime()`, printing one summary
line when the node reaches leader role. Enabled by `-Doms.replay.report=true`; off by
default, so normal operation is unchanged and the Never-do rule on non-determinism in
the service is respected (the wrapper lives in `cluster-node`, not `cluster-service`).

- Alternative — timing the whole process start minus an empty-journal baseline:
  rejected; it folds JVM startup and election noise into the number.

### D4 — Correctness definition

A replay is correct when (a) the number of applied heartbeats equals the manifest
count, and (b) the sequence of echoed timestamps equals `golden-outputs.txt`. Replaying
twice must produce identical outputs. When real state exists later, a state-hash
assertion is added; the spec only pins what exists today.

## Risks / Trade-offs

- **Frame-format coupling (D2).** An Aeron upgrade could change segment layout in
  principle; the committed tape plus its replay test fails loudly if so. Fallback
  recorded: switch app-mode to `AeronArchive.replay()`.
- **Benchmark asymmetry.** App mode excludes driver and consensus costs by design; the
  two numbers answer different questions (pure rebuild speed vs production recovery
  time) and the benchmark output must label them as not directly comparable.
- **Binary fixture in git.** Immutable by rule — a tape is never edited or
  regenerated in place; a new scenario is a new tape file. Repo growth is bounded and
  deliberate.
- **Wrapper timing uses `System.nanoTime()`** in `cluster-node` (allowed tier);
  determinism rules apply only to `cluster-service`, which stays pure.
